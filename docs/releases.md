# Versioning and releases

Pong Ladder has one source of truth for a release: [`src/data/releases.json`](../src/data/releases.json).

That file feeds every place a version or a set of release notes appears:

- the version shown in the application footer;
- the in-app **What's new** page at `/changelog`;
- the body of the published GitHub Release;
- the `version` field in `package.json` and `package-lock.json`.

Adding a release means editing that one file. Nothing else restates the version number or the notes.

## The release data

Each entry describes one release, newest first:

```json
{
  "version": "1.1.0",
  "date": "2026-09-14",
  "summary": "Optional one-line framing for the release.",
  "changes": {
    "new": ["Something users can now do."],
    "improved": ["Something that got better."],
    "fixed": ["Something that no longer misbehaves."]
  }
}
```

Rules enforced by `parseReleases` in [`src/lib/release-notes.ts`](../src/lib/release-notes.ts), and covered by `tests/release-notes.test.ts`:

- `version` is `MAJOR.MINOR.PATCH`, with no prefix and no pre-release suffix.
- `date` is `YYYY-MM-DD`, treated as a calendar date and formatted in UTC.
- Entries are listed newest first, and no version appears twice.
- Only the `new`, `improved`, and `fixed` groups exist, and every release lists at least one change.

Invalid data fails `npm test` and the production build rather than rendering a broken changelog.

## Writing the notes

The notes are read by players, not by contributors. Write what changed for someone using the ladder.

- Describe user-visible behavior, in plain language, one change per bullet.
- Leave out dependency bumps, CI changes, refactors, and commit-by-commit history.
- Mention an internal change only when a player would notice it.
- Never include environment names, hostnames, credentials, or other deployment detail.

GitHub's generated release notes are a reasonable prompt for remembering what landed, but they are raw commit history and are not published as-is.

## Cutting a release

1. On a branch off `dev`, add the new entry at the top of `src/data/releases.json`.
2. Run `npm run release:sync` to write the version into `package.json` and `package-lock.json`.
3. Open the pull request into `dev` as usual. `npm test` fails if the package metadata has drifted from the newest entry.
4. Promote `dev` to `main` through a pull request, as described in [CONTRIBUTING.md](../CONTRIBUTING.md#branch-and-release-flow).
5. Tag the merge commit on `main` and push the tag:

   ```bash
   git switch main
   git pull --ff-only origin main
   git tag "v$(npm run --silent release:version)"
   git push origin "v$(npm run --silent release:version)"
   ```

Pushing the tag is the only manual release step. [`.github/workflows/release.yml`](../.github/workflows/release.yml) takes it from there.

## What the release workflow guarantees

The workflow runs on `v*` tags only, so ordinary commits and merges into `dev` never publish a release. Before it publishes anything it verifies that:

- the tagged commit is an ancestor of `main`, so the tag identifies an artifact that was actually promoted to production;
- the tag matches the newest entry in `src/data/releases.json`;
- `package.json` and `package-lock.json` agree with that same entry.

If any check fails the workflow stops without creating a release, so the application can never report one version while GitHub advertises another. The release body is generated by `npm run release:notes` from the same entry the application renders.

## Version numbers

Pong Ladder uses semantic-version-style numbering from the player's point of view:

- **major** for a release that changes how the product is used;
- **minor** for new capability;
- **patch** for fixes and small corrections.

## Development builds

Only production builds print a bare version. Every other build renders `Pong Ladder v1.0.0 (dev)`, so a local or preview build is never mistaken for a deployed one. The footer never exposes commit hashes, branch names, or environment details.

## Localization

Coordinated with PL-23:

- Application-owned labels — **What's new**, **New**, **Improved**, **Fixed** — are defined in `src/lib/release-notes.ts` and `src/features/changelog/ChangelogPage.tsx`, so they can be localized alongside the rest of the interface.
- The product and version identifier, for example `Pong Ladder v1.0.0`, is not translated.
- Release-note content is authored in English only. It is published verbatim to GitHub Releases, and translating it would mean maintaining a second copy that can drift from the published release. If localized notes are wanted later, the entry gains per-locale change lists so both the application and the GitHub Release still come from this one file.

## Commands

| Command | Purpose |
| --- | --- |
| `npm run release:version` | Print the current version, for example `1.0.0`. |
| `npm run release:notes` | Print the GitHub Release body for the current version. |
| `npm run release:sync` | Write the current version into `package.json` and `package-lock.json`. |
| `npm run release:check` | Fail when package metadata has drifted from the newest release entry. |
