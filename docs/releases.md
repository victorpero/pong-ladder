# Versioning and releases

Pong Ladder has one source of truth for a release: [`src/data/releases.json`](../src/data/releases.json).

That file feeds every place a version or a set of release notes appears:

- the version shown in the application footer;
- the in-app **What's new** page at `/{locale}/changelog`;
- the body of the published GitHub Release;
- the `version` field in `package.json`, and both root version entries in `package-lock.json`.

Adding a release means editing that one file. Nothing else restates the version number or the notes.

## The release data

Each entry describes one release, newest first:

```json
{
  "version": "1.1.0",
  "date": "2026-09-14",
  "summary": {
    "en": "Optional one-line framing for the release.",
    "sv": "Valfri sammanfattning av versionen."
  },
  "changes": {
    "new": [{ "en": "Something users can now do.", "sv": "Något användare nu kan göra." }],
    "improved": [{ "en": "Something that got better.", "sv": "Något som blivit bättre." }],
    "fixed": [{ "en": "Something that no longer misbehaves.", "sv": "Något som inte längre krånglar." }]
  }
}
```

Rules enforced by `parseReleases` in [`src/lib/release-notes.ts`](../src/lib/release-notes.ts), and covered by `tests/release-notes.test.ts`:

- `version` is `MAJOR.MINOR.PATCH`, with no prefix and no pre-release suffix.
- `date` is a real `YYYY-MM-DD` calendar day, validated by a UTC round trip so an impossible date such as `2026-02-31` is rejected rather than silently rendered as another day, and formatted in UTC.
- Entries are listed newest first, and no version appears twice.
- Only the `new`, `improved`, and `fixed` groups exist, and every release lists at least one change.
- Every summary and change entry carries text for every supported language.

Invalid data fails `npm test` and the production build rather than rendering a broken changelog.

## Writing the notes

The notes are read by players, not by contributors. Write what changed for someone using the ladder.

- Describe user-visible behavior, in plain language, one change per bullet, in every supported language.
- Leave out dependency bumps, CI changes, refactors, and commit-by-commit history.
- Mention an internal change only when a player would notice it.
- Never include environment names, hostnames, credentials, or other deployment detail.

GitHub's generated release notes are a reasonable prompt for remembering what landed, but they are raw commit history and are not published as-is.

## Cutting a release

1. On a branch off `dev`, add the new entry at the top of `src/data/releases.json`.
2. Run `npm run release:sync` to write the version into `package.json` and `package-lock.json`.
3. Open the pull request into `dev` as usual. `npm test` fails if the package metadata has drifted from the newest entry.
4. Promote `dev` to `main` through a pull request, as described in [CONTRIBUTING.md](../CONTRIBUTING.md#branch-and-release-flow).

Step 1 is not optional: a promotion whose version was already released at another commit fails, because the tag, the release, and the versioned image would otherwise describe different code.

That is the whole process. There is no manual tagging step: merging to `main` is the release. [`.github/workflows/release.yml`](../.github/workflows/release.yml) tags the promoted commit, publishes the GitHub Release, and only then builds and pushes the production image.

## What the release workflow guarantees

Promotion to `main` is the single production path, and the workflow runs it as one sequence:

1. **Publish the release.** The version is read from `src/data/releases.json`, `package.json` and both root entries in `package-lock.json` are verified against it, and the tag `vX.Y.Z` is created at the promoted commit and published as a GitHub Release with notes generated by `npm run release:notes`.
2. **Publish the image.** Only if the first job succeeded, the production container image is built and pushed as `latest`, the commit SHA, and `vX.Y.Z`.

This ordering is what keeps the version honest. The production image is what makes a version live, and it cannot be published unless the matching tag and GitHub Release already exist. If the release step fails, nothing is deployed and production keeps serving the previous version rather than one GitHub does not advertise.

**Every promotion to `main` must carry a new version.** The production image is published as `vX.Y.Z` as well as `latest`, so the tag for the promoted version has to resolve to exactly the promoted commit. If `src/data/releases.json` still names a version that was already released at an earlier commit, the workflow stops and asks for a new entry rather than rebuilding `vX.Y.Z` from different code. Promoting to `main` is releasing; if a change is worth deploying, it is worth a version.

Two paths are still no-ops rather than failures: re-running the workflow for a commit whose release is already published does nothing, and a tag that exists for *this exact commit* without a release — an earlier run that stopped part way — is completed by publishing its release.

Merges into `dev` do not run this workflow, so ordinary development never publishes a release or a production image.

## Version numbers

Pong Ladder uses semantic-version-style numbering from the player's point of view:

- **major** for a release that changes how the product is used;
- **minor** for new capability;
- **patch** for fixes and small corrections.

## Development builds

Only production builds print a bare version. Every other build renders `Pong Ladder v1.0.0 (dev)`, with the marker taken from the active language, so a local or preview build is never mistaken for a deployed one. The footer never exposes commit hashes, branch names, or environment details.

## Localization

Release notes are written once per supported language, exactly like the interface dictionaries, so a Swedish reader never meets an English changelog inside an otherwise Swedish application.

- Every `summary` and every change entry is an object with one string per language in `SUPPORTED_LOCALES`. A missing or blank language fails `parseReleases`, and `tests/release-notes.test.ts` asserts that every entry in `releases.json` is complete in every language.
- Application-owned labels — **What's new**, **New**, **Improved**, **Fixed**, the back links, and the development marker — live in `src/lib/i18n/dictionaries/*.ts` under `changelog` and `footer`, so the dictionary parity test covers them like any other interface text.
- The product and version identifier, for example `Pong Ladder v1.0.0`, is never translated.
- Release dates are formatted per language, in UTC, so the same calendar day is shown everywhere.
- The published GitHub Release body is rendered in English by default, because the repository has an international audience. `npm run release:notes sv` renders the Swedish body from the same entry. Both come from the same data and the same headings the application uses, so no language can drift from another.

Adding a language to `SUPPORTED_LOCALES` makes every existing release entry incomplete, which fails the tests until the notes are translated. That is deliberate: a half-translated changelog should not reach production.

## Commands

| Command | Purpose |
| --- | --- |
| `npm run release:version` | Print the current version, for example `1.0.0`. |
| `npm run release:notes` | Print the English GitHub Release body for the current version. |
| `npm run release:notes sv` | Print the same body in another supported language. |
| `npm run release:sync` | Write the current version into `package.json` and both `package-lock.json` root entries. |
| `npm run release:check` | Fail when any of those three fields has drifted from the newest release entry. |
